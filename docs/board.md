# Using the board

What's on the board and how to work it. Settings are in [settings.md](settings.md), agents in [agents.md](agents.md).

## Getting started

- **Setting up:** a new board opens the setup guide by itself (`#welcome`): your name, your first projects, Claude Code's MCP server with a check that an agent really reached the board, the prompt that sets each project up for agents, notifications and start on login, and how the board works. Every step can be skipped. Until each is done or skipped, "Finish setting up" sits at the top of the board; Settings → Getting started brings the guide back any time. A board already in use is never sent there. Empty boards and projects say what goes there and how to get it there.
- **Projects:** add one in Settings (at the bottom of the projects strip on the left), or `wb project <slug> <path> "Name"`. Items added from inside that path belong to it; the board shows each project's git state (uncommitted files, unpushed commits, unmerged branches, worktrees). A finished project can be archived (see [Settings → Projects](settings.md)).
- **Logos:** if the one found is wrong, `wb project <slug> --icon path/in/repo.svg` (`--icon ""` to look again).

## Layout

- **Layout:** projects down the left edge (each shows its logo, found in the repo: `icon`, `logo`, `app-icon` or `favicon` files, else its initials; the badge counts what waits on you). Next to it, a foldable sidebar with the project's reports and links. Search sits at the top (Ctrl K or `/`): items with their notes, goals, reports' text and links of the selected project, or of everything under "All". The board itself is one section per kind (decisions, setup, checks, …), then "Done lately" and the repository state; every section folds and stays as you left it. "Everything / Needs you / With agents" narrows it to who has to act.
- **Bookmarks:** the "Links" part of the sidebar, folded by group. "+" adds one (for one project or every project, optionally in a group), the pencil then a click edits or deletes. The server fetches each site's favicon once and keeps it in the database; paste an icon address in the dialog when the site's own is wrong, or use "Refresh icons" in edit mode. From a terminal: `wb links`, `wb link "Label" <url> [--project P | --all] [--group G] [--icon <url>]`, `wb relink <id> …`, `wb unlink <id>`.
- **Status trackers** sit under the project's name in the sidebar: quotas and states that change on their own, like EAS builds used this month or GitHub Actions minutes left (see [trackers.md](trackers.md)). With the sidebar folded each is a ring; point at one to see it in full.
- **Notifications:** the bell above the board turns on desktop notifications for this browser: something new needs you, an agent finished, got stuck or can carry on, a report was added or updated. They show only while the board isn't the window in front, and never for changes made in that same tab. Settings → Notifications picks which, and quiet hours.

## Items

- **Items** are named `wb-xxxx` (e.g. `wb-k3f9`); click one on the board to copy it into a prompt ("Do wb-k3f9"). Commands also take the bare `k3f9` and the old numbers.
- **Reading an item:** clicking a card (or a line in Today, a search result, a ref anywhere) opens the item as a page to read, in a sheet from the right with the board dimmed behind it; on a phone it fills the screen. Its address is `#item/wb-k3f9`, so a link or a reload opens it, and closing it (Esc, ×, a click on the board) goes back to where you were. From the top:
  - one line of context: the ref (click to copy), the kind, the project, who filed it and when, and its status when it isn't to do; then the title, which you click to change (Enter or clicking away keeps it);
  - for an ask with a default, one quiet line: "If you say nothing, it goes ahead with X on Thu 26 Nov", with **change date** and **remove** (highlighted when that's within a day);
  - the brief at reading width, with its pictures under it. **Edit** (or E) opens it as markdown; Ctrl+Enter or clicking away saves it, Esc puts it back;
  - what it asks of you. A decision: its choices as big buttons, numbered 1–9 (press the number), the recommended one outlined; one click answers it at once. When several can be picked: ticks, then one **Answer**. **Or answer in your own words** goes to the reply box. A review or notice: **No objections** / **Got it** (A) and **Object…** (O). A check: its steps, with how the latest run went on each, and **Run it** (or Continue). When the board starts agents and the agent can start now, a **resume the agent** tick next to the answer sends it and starts the agent in one go;
  - **Done** (M), **Drop** (X), and for what's yours **Later** (D: tomorrow, in 3 days, next week or a day; out of the queue until then) and **Give back** (G: back to the agent with a line, "You decide, with your recommendation" when empty);
  - the agent's run, when there is one (near the top while it runs);
  - the history as a thread, oldest first: agents' notes, and yours set apart; field changes are small grey lines, and several in a row fold into "4 changes". Long threads show the last few, with "Show N earlier";
  - one reply box: on an ask, Enter answers in your words (a decision) or objects (a review or notice); otherwise it adds a note. Shift+Enter is a new line; "Add a note instead" switches it.

  Beside it (under it on a phone, folded) are its properties, each changed in place and saved at once: status, who acts, kind, priority, project, area, goal (when the project has goals), branch, session (with a link to open it), a decision's choices, what happens if you say nothing and on which day, what it waits on and what waits on it (click to open), its code (pull requests and commits), and the ruling its answer made. Nothing waits for a Save. J and K open the next and previous item in the list you opened it from (the board's cards, the queue, Today's lines, search results; nothing from elsewhere), 1–9 pick a choice, E edits the brief, Esc closes. While it's open the board keeps polling, and the item updates as agents write, never in a box you're typing in.
- **A new item** (New, top right): the same page with the title and brief open, and kind, project, who acts (it follows the kind until you pick) and priority beside them; a decision also takes its choices. **Create** (or Ctrl+Enter) files it.
- **Details and notes** are markdown: `-` and `1.` lists (indent to nest; a blank line between items is fine), `**bold**`, `#` headings, `>` quotes, `` `code` ``, ``` blocks and links. A note only counts as markdown when it has more than one line.
- **Pictures on items:** agents attach screenshots to show what they mean (`attach_image` over MCP, or `wb image add <ref> shot.png "What to look at"`; `--image`/`--caption` on `wb add`). You add your own in the item: **Add image** under the brief, or paste one (a screenshot straight from the clipboard) or drop files anywhere on it. A new item holds them until you create it. They show under the details with their captions, which you edit in place (Enter keeps one), a click opens one full size, and a card shows how many it has. Remove takes one off. An agent reads one with `get_image` or `wb image save <id> <file>`. Only PNG, JPEG, WebP and GIF get in, checked by the file's contents, at most 20 MB. They live in the database, so anything over 500 KB is shrunk to 2000 px on its longer side first, to keep backups small.
- **Items you can follow:** every item for you has to make sense without opening anything else. The rules are in the MCP server's instructions and `add_item`, and in `wb guide` for agents on the command line. When an agent files something for you with no real body, it's refused. When it points at a .md file or PLAN section, uses internal codes or source paths, or talks about something on screen with no picture, the item is saved and the agent is told what to fix. These are guesses, so nothing but an empty brief is refused, and items you file yourself are never checked.
- **Decisions with choices:** `wb add "Sync strategy" --option "CRDT" --option "Last write wins"` files a decision for Kostas with those choices. Its card says what the agent recommends ("recommends: CRDT") but has nothing to click: you answer in the item, after reading it, where one click answers and hands it back to the agent; `wb show` prints the answer, and `wb ls` shows it after the title. `wb answer <ref> "choice"` (or its number) answers from a terminal. Only checks and setup steps keep a tick on their card, to mark them done.
- **Code on items:** commits whose message mentions `wb-xxxx`, and pull requests whose title, body or branch name does, show on the item: a count and the newest PR's state on the card, the list with review and checks among its properties. Put the ref in commit messages and PR titles. Pull requests come from `gh`, asked at most every 90 s per project.
- **Stale work:** an agent's item is flagged when it's doing with no sign of life for a day ("stalled": no note, and no MCP or `wb` call about it, see [Is it running?](agents.md#is-it-running); never while a run the board started is on it), or waiting for 7 days. Your own items never are: how long an ask has waited on you is its age, not a warning. The card shows an amber badge ("stalled 3 d"), each kind's header counts them ("2 stale"), `wb ls` marks them ⚠, and `project_overview` and the `status` prompt list them. Every item the API and the MCP tools return has `stale`: `null` or `{ why, since }`. The rule and its thresholds are in `stale.ts`.

## Waiting on another item

an item that's blocked says what it waits on, so answering that item lets the work carry on by itself. `wb wait <ref> "why" --on wb-xxxx` (repeat `--on` for more; `wait_item` takes `on`) marks it waiting and links it; when an agent needs something from you, `wb add "…" --kind decision --blocks <its item>` (or `add_item` with `blocks`) files your item and makes its own wait on it in one go. When the item waited on is answered (a decision), finished or dropped, whatever waited only on it goes back to **todo** with a note in its history ("Unblocked: wb-k3f9 was answered: Last write wins"); one that waits on several carries on when all are dealt with, and is told about each meanwhile. An item that leaves waiting by any other way (an agent picks it up, you change its status) waits on nothing. The item lists "Waits on" and "Blocks" among its properties (click one to open it), a card for you says "unblocks N", and what unblocks the most comes first within a priority in your lists, `list_items` (`unblocks`), `wb ls`, `project_overview` and `/mcp__wb__status`. `wb edit <ref> --on wb-xxxx` / `--not-on wb-xxxx` and `update_item`'s `waits_on` / `not_waiting_on` add and remove links, `get_item` and `wb show` list both ends. An item can't wait on itself, on something already dealt with, or round a circle. It's one table (`item_links`) and the code is `links.ts`; a notification "An agent can carry on" (Settings → Notifications) says when it happens.

## Asks that don't block

Agents ask faster than anyone answers, so most of what they leave for you doesn't stop their work:

- **Notices** (kind `notice`): "here's what changed, object if you want". They're yours by default but never count as waiting on you: not in the badges, "Needs you", the app's tray count, notifications or `wb ls --mine` (which counts them after the list). They have their own section on the board; in the item, **Got it** closes one and **Object…** takes a line in the reply box that goes back to the agent as a to-do, with your words in its history. `wb seen <ref>` and `wb object <ref> "why"` do the same from a terminal; a review has them too (No objections, Object…).
- **A default and a deadline** on decisions, reviews and notices: what happens if you say nothing (`--default`, MCP `default`; for a decision with options, one of them), and by when (`--decide-by 2026-11-14` or `"in 3 days"`; one with a default and no date gets Settings → You and your day's wait, 3 days). The card says "Goes ahead with X on Fri, Nov 14", highlighted within a day; the item says it under its title, where you change the date or remove it, and its properties also change what goes ahead. When it passes, the default goes ahead exactly as if you had clicked it: a decision is answered with it and handed back, a review closes with no objections, a notice closes as seen, and the history says "No answer by Fri 14 Nov: went ahead with X". The board does it every minute, and `wb` and the MCP server do it before they read anything, so it happens with the board off too. Without a default nothing ever goes ahead by itself.
- **Every ask from an agent has a way out:** a review an agent files without a default gets one (it closes with no objections at the usual wait), and so does a notice (it closes as seen). A decision's recommendation becomes its default (pick many: the recommended list). A decision with neither is refused unless it's priority 1, with what to do instead: give a recommendation, or file it as priority 1 if it can't go ahead without you (money, accounts, something that can't be undone). The same holds when an agent's `update_item` or `wb edit` makes an item one of these asks, and the reply tells the agent what default it got. Checks and setup don't change (they're things you do), nor do asks already on the board, nor anything you file yourself. The MCP server, `wb add` and the page's New item all file through one function (`filing.ts`).
- **Pick several:** a decision with `--pick many` is answered with ticks and one Answer button (`wb answer <ref> 1 3`, or `none`); the agent's `--recommend` options start ticked. `answer` stays readable text ("Change password; Signed-out message") and `picks` keeps the list. A one-pick decision can mark its recommended option too, on its button.
- **A cap:** a project takes at most 20 open asks (decisions, reviews, checks, setup) that agents filed for you; past it, an agent's `add_item` or `wb add` is refused with what to do instead (bundle into one pick-many decision, send a notice, decide with a default, or drop one). Notices, priority 1 and your own items always go on. Settings → You and your day changes the number (0: no cap).

## Goals

say what a project's work is for (a release, a launch): a title, a short description, an optional target date, and the items that serve it. With a project selected, its open goals sit above the board: progress (done of all), the target date, how many items wait on you, and what blocks it (open items for you, and agent items that are waiting). Click a goal to show only its items (the address says `#goal/3`, so a reload keeps the filter) and see everything holding it back; click it again to go back. The pencil on a goal, or "+", opens a small dialog: title, date, description, "The active goal" (agents pick its work first; with none marked, the first goal is), Earlier/Later to reorder, Mark done, Drop. Under All, one line per project with an active goal. An item has a Goal picker among its properties, and a card names its goal when its project has more than one open. Agents have `list_goals`, `add_goal`, `update_goal` and a `goal` on `add_item`, `update_item` and `list_items` (its number or exact title); `project_overview` lists goals with progress and blockers, and `/mcp__wb__next` prefers work on the active goal. Agents are told not to create goals for you: they propose one as a decision. From a terminal: `wb goals`, `wb goal add "First release" --due 2026-12-01`, `wb goal 3 --done` (or `--drop`, `--active`, `--title`, `--due`), `wb add "…" --goal 3`, `wb edit <ref> --goal none`, `wb ls --goal 3`. Search finds goals, and day pages show an item's goal. The queue of what waits on you can order by goal: `GET /api/goals/items` gives each item's goal and its rank (1 = the active goal), `itemGoals` in goals.ts the same in code.

## Rulings

what you already decided, one line each ("Traditional is the default melisma style"), so agents read it instead of asking again. Answering a decision drafts one from its question and answer, marked "draft"; the next agent that picks the item up rewrites it as one clear line. They're in the "Rulings" part of the sidebar (folded, like Links) and in their own view: search, Edit, Retire (it no longer holds; Retired brings it back), Add a ruling. The item shows the ruling its answer made among its properties, and search finds them, accents or not. Agents read them in `project_overview`, `/mcp__wb__work-on` (the ones that bear on the item), `list_rulings` and `wb://rulings/{slug}`, and write them with `add_ruling`, `update_ruling`, `retire_ruling`. When an agent files a decision or review that looks like one already ruled on, it's saved, and the agent gets the ruling and its item back: "Kostas already ruled: … (wb-xxxx, 25 Oct). If this is answered by that, drop the item." The match is by shared words (accents and case don't matter, so Greek works), tuned on the board's own decisions to fire rarely. From a terminal: `wb rulings`, `wb rule "text" [--item <ref>]`, `wb rule <id> "text"`, `wb unrule <id>`. Answers given before rulings existed got their drafts once, when the board first opened with them.

## Running a check on the phone

a check is something you try on a device, so it runs here one step at a time. **Run it** on a check's card, or in the item under its steps, opens `#check/<ref>`: the brief's numbered list becomes the steps (nested bullets stay with their step; a brief with several lists, like "Setup" and "What to check", is all of them, each step under its heading; no list is one step, the whole brief), and "What right looks like" / "What wrong looks like" show above the steps and with the last one. Each step has big **Pass** / **Fail** buttons at the bottom, a few words (needed on Fail, unless there's a photo), and **Add photo** (the phone's camera or gallery; shrunk before it's sent, captioned "Step 3: Try a date… — failed: your words" and kept on the item). Every answer is saved on the server as you give it, so you can start on the phone and finish at the desk; **Start over** clears the run and its photos. **Finish** when every step has an answer: all passed → the check is done, with a note ("All 6 steps passed on Safari on iPhone"); any failed → a **bug** for an agent per failed step in the same project ("<check>: step 2 fails", with the step, what should happen, your words and the photos copied on), and the check **waits on those bugs** (see [Waiting on another item](#waiting-on-another-item)), so it comes back to your to-do by itself when they're finished, to run again (a new run starts then). `get_item` and `wb show` give agents the latest run's results per step. The tables are `check_runs` and `check_run_log`; the code is `checkruns.ts` and `ui/checkrun.js`; `openCheckRun(ref)` opens a check for running from anywhere in the page. API: `GET /api/items/<id>/check`, `PUT …/check/steps/<n> {result, words}`, `POST …/check/steps/<n>/photos {data}`, `DELETE …/photos/<image>`, `POST …/check/finish`, `POST …/check/reset`.

## Today

(the button next to Usage, `#today`, or the T key): a one-screen brief for the project you're on or all of them, since your last visit (kept in this browser; a new visit starts after an hour away, the first one counts the last 24 hours; "Start from now" resets it). **Needs you**: how many wait on you and how many are new, the ones that unblock agent work (when an item has `unblocks`), the newest and the oldest. **Done by agents**: what finished, by project, with the finishing note's first line and the commit count. **Stuck**: agent items that are waiting or stale (when an item has `stale`). **Coming up**: open items whose deadline (`decide_by`, when items have one) is within three days. **Reports updated**, day pages left out. Empty sections aren't drawn; when nothing happened it says so in one line. Every line opens the item or report. The quiet-hours summary notification ("While you were away") opens it. `GET /api/today?project=&since=` gives the finished items and the updated reports (`today.ts`); the rest comes from the open items.

## One at a time

(queue mode, `#queue`): **Go through them one by one** on the board's Needs you and in Today's Needs you, or the Q key, for the project you're on or all of them. One item fills the screen: its kind, project, how long it has waited, its goal, "unblocks N", and what goes ahead by itself and when; then the brief's opening (its first paragraph, cut at a sentence) and **Read all** (R) for the whole brief, its pictures and the latest notes. A check lists its steps. Then one key or tap each: a choice (1–9; on a pick-many decision 1–9 tick and Enter answers the ticked ones, the recommended ones ticked to start), Enter or A for the recommended answer, No objections, Got it, It works or Done; O for your own answer, an objection, "Didn't work" or a problem (back to the agent with your line); D to **defer** (tomorrow, in 3 days, next week or a day you pick: it leaves the queue on the phone and the desk alike until that day, still counts as waiting on you, and the card says "deferred to …"); G to **give back** to the agent with a line ("You decide, with your recommendation" when empty: owner agent, to do, the line in its history, its deadline cleared); X to drop; → or S to skip, ← back, Esc to leave. Each says what it did and can be undone (U) until the next one: it's sent when you act again, leave, put the phone away, or after 10 seconds. The order: priority 1 first, then what unblocks the most, then the active goal's items, then deadlines in the next three days, then P2 before P3, then the oldest; similar asks come one after another and say so ("3 more like this next · same area: sync"): same project and area, or titles alike (rulings' word matcher), at most 8 together. Notices come after the asks, for a quick Got it or objection. "12 cleared · 30 to go" and a thin bar show how far you are; at the end, "Nothing waits on you" (or how many are deferred until when) and what this pass cleared. On a phone it's full screen with the buttons at the bottom; swipe the card right for the big button's action, left to skip. `GET /api/queue?project=` gives the order (`queue.ts`); `POST /api/items/:id/defer {until}` and `/give-back {text}` are the two new actions; deferring and giving back are lines in the item's history, so agents need nothing new.

## Usage

(the button next to Vault, or `/usage`): what Claude has used, for the project you're on or all of them: cost at Claude API list prices, tokens by type, a chart split by project, model or app, when in the week you work, and a breakdown by project, session, model, day or app. It reads Claude Code's transcripts in `~/.claude/projects` (the desktop app, the CLI and the Agent SDK all write there), counts each response once, and opens only on this computer. Folders that aren't a board project are listed under "Other folders"; a worktree counts with its project.

## From the phone

`wb serve --lan` (or the app's tray item Phone access) listens on your network too, and only phones you pair get in. Settings → Privacy and security → Phones → **Pair a phone** shows a QR code and a code (`XXXX-XXXX`) that work once, for 10 minutes. Scan it with the phone's camera, or open the board's address on the phone and type the code; name the phone (it suggests one, like "Safari on iPhone") and it stays paired. The phone keeps a random token in a cookie its pages can't read (HttpOnly, SameSite=Strict, for 400 days, renewed each time it opens the board); the board keeps only the token's hash. Anything else on the network gets the pairing page and the app's name and icons, nothing more: not the page's scripts, the API, reports or pictures. Wrong codes: after 5 from one address it has to wait 10 minutes, and after 10 in all the code stops working. A paired phone uses the board like this computer does (answers, notes, new items, pictures), except what answers only this computer: the vault, data sources, changing settings, shares, usage and MCP. This computer (localhost) needs no pairing. Settings lists the paired phones (name, when paired, last seen, from which address) with **Remove**, which shuts one out at once, and **Remove all**; `wb devices` and `wb unpair <id|all>` do the same from a terminal.

- **Plain http on your network:** the token, and everything the phone reads and sends, cross the network without encryption, so use `--lan` only on a network you trust. That's also why the vault never opens from the phone.
- **As an app on the phone:** "Add to Home Screen" (the share menu in Safari, the menu in Chrome) puts the board on the home screen with its own icon, from a web app manifest and the iOS tags. Over plain http, browsers allow no service worker and no install prompt (they need https or localhost), so it doesn't work offline, Chrome on Android may make it a plain shortcut that opens in Chrome, and there are no notifications. An iPhone's home-screen app can keep its own cookies apart from Safari: if it opens on the pairing page, pair it there once more.
- **Other web pages can't change the board:** every write to its API must be JSON, and a browser won't send that from another site (or from a report page) without asking the board first, which it never allows. Anything else gets 415.

## Your data

`workbench.db` next to this file (gitignored). The board copies it to `backups/` once a day and keeps the newest 14 (Settings → Data → Backups kept); `wb backup` makes one now and `wb backups` lists them. `wb export > file.json` writes everything as JSON. To restore, Settings → Data → Restore gives the exact commands for this computer (in short: stop the board, copy a backup over `workbench.db`, remove `workbench.db-wal`/`-shm`, start it). Vault secrets stay encrypted in backups.

## Start on login

(optional): a user service. Settings → Health says whether it's set up, and gives the commands below with this computer's paths filled in.

```ini
# ~/.config/systemd/user/workbench.service
[Unit]
Description=Workbench board

[Service]
ExecStart=/home/kostas/.bun/bin/bun /home/kostas/Projects/workbench/src/server.ts
Restart=on-failure

[Install]
WantedBy=default.target
```

Then `systemctl --user enable --now workbench`.
